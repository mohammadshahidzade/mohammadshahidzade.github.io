01 / THE PROBLEM

Fast accelerators can still produce slow systems.

Linux and other operating systems were built around CPUs as the primary compute elements. Hardware accelerators are typically treated as peripheral devices, reached through drivers, memory copies, interrupts, and CPU-managed scheduling. For fine-grained or latency-sensitive work, these software paths can erase much of the accelerator’s advantage.

MEERKAT makes these costs measurable. It provides a configurable FPGA platform where operating-system functions can be migrated between software and hardware, exposing the communication, invocation, interrupt, and scheduling “taxes” paid by heterogeneous applications.

02 / THE SYSTEM

A research platform built from the processor outward.

Linux appsMEERKAT O/S layerCVA5 + HW supportAccelerators

The framework begins with the FPGA-optimized CVA5 RISC-V core and extends it into a complete Linux-capable system. The platform adds privilege modes, virtual memory, interrupt infrastructure, multicore-capable SoC support, cache coherence mechanisms, and direct accelerator integration.

Four overheads, four co-designed responses

  • Communication: shared virtual memory mechanisms, hardware-assisted address translation, and scatter-gather page transfer reduce copying and allow accelerators to operate on application data.
  • Invocation: lightweight custom-instruction paths reduce the cost of starting work and checking completion.
  • Interrupts: an adaptive policy selects between polling and interrupts based on expected accelerator latency.
  • Scheduling: CPUs and multiple accelerator instances are managed as a unified pool of compute resources rather than separate device classes.
03 / CONTRIBUTIONS

Cross-layer work from RTL to runtime policy.

  • Built and evaluated MEERKAT on a Xilinx VCU118 at 100 MHz, booting through LiteX BIOS and OpenSBI into Linux.
  • Designed compact hardware support for virtual-address communication, including CIVAT, HMAC, and scatter-gather mechanisms.
  • Measured the difference between accelerator execution time and application-level performance under real O/S paths.
  • Evaluated scheduling across CPU cores and replicated accelerators, showing why the best compute element depends on both task latency and resource availability.
  • Produced the M.A.Sc. thesis and an HPCA 2027 submission; the conference decision is pending.
04 / RESULT

The operating system belongs in the accelerator conversation.

The results show up to 260× lower communication overhead, up to 71× faster hot-page translation, and 1.5–5.8× lower application wall-clock time compared with a worker-based scheduler across evaluated configurations. More importantly, they show that accelerator speed alone does not determine system performance: resource availability, operating-system overhead, and scheduling policy matter together.
